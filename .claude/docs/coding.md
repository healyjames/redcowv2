# Coding Guidelines

> Generated by `/install`, expanding the rules already stated in `CLAUDE.md`. Re-run
> `/clarify coding` any time to refine it further.

## Language & style decisions

- No data mutation — immutable data structures only where possible.
- Pure functions wherever possible, especially anything in `src/libs`.
- No nested if/else — use early returns or composition instead.
- No comments — code should be self-documenting. The only accepted exceptions: explaining a regex
  that isn't instantly readable, or explaining a third-party import/quirk (e.g. a brand's font
  loaded from an Adobe stylesheet under `src/assets/<brand>/fonts`).
- Prefer options objects over positional parameters (especially past ~2-3 args).
- Use array methods (`map`, `filter`, `reduce`) over loops.
- TypeScript strict mode always (`astro/tsconfigs/strict`). Avoid `any` at all costs. `unknown` is
  allowed only with a comment explaining why, if the reason isn't obvious.
- Unused parameters required by an interface but not used in the implementation: prefix with an
  underscore (e.g. `_context`) rather than removing them or suppressing the warning another way.

## Error handling

- API routes (`src/pages/api/**`) validate input at the boundary and return explicit error
  responses (4xx for validation, 5xx for unexpected failures) — don't let unvalidated input reach
  `src/libs`.
- Don't swallow errors silently. If a caught error isn't re-thrown or surfaced, that's a code-review
  finding.

## Naming & structure

- Vertical slice / feature-folder layout (see `.claude/docs/architecture.md`) — co-locate a
  feature's page, component, and tests rather than splitting by technical layer.
- `.astro` components for page-level / mixed HTML+CSS+JS composition; React only for the
  interactive islands under `src/components/client`.
- Keep `.astro` component logic in the frontmatter section; use TypeScript there and in script
  tags.
- Only hydrate what needs interactivity (Astro's islands architecture) — pick the narrowest
  `client:*` directive that satisfies the need.

## EditorConfig rules

- 2-space indentation
- UTF-8 charset
- Insert final newline
- Trim trailing whitespace
- Markdown: preserve whitespace, no line length limit

## Banned / discouraged

- `any` — breaks the strict-mode guarantee; use a real type or a commented `unknown`.
- Nested if/else — replace with early returns or composition.
- Comments that restate what the code already says — if it needs explaining, restructure it
  instead (see `.claude/skills/code-review` and the `doc-writer` agent's Code Comments guidance).
- Mutating shared/brand data in place — always derive a new value.
- Hardcoding one brand's content/styling in shared code instead of reading it from
  `src/assets/<brand>` (see `.claude/docs/architecture.md`).
