# Architecture Guidelines

> Generated by `/install` from the existing project structure. Re-run `/clarify architecture` any
> time to refine it further.

## Pattern

- **Pattern:** Vertical slice / feature folders. Code is organised by what it does
  (page, API route, component, brand) rather than by technical layer.

## Boundaries & dependency rules

- `src/libs/{email,types,utils}` holds framework-agnostic logic — pure functions and types with no
  dependency on Astro, React, or the request/response lifecycle. Anything reusable across pages,
  API routes, or components belongs here, not duplicated inline.
- `.astro` files (`src/pages`, `src/layouts`, `src/components`) keep frontmatter thin: fetch/shape
  data, delegate real logic to `src/libs`. Don't grow business logic inside a component's
  frontmatter.
- Only components that need client-side interactivity live under `src/components/client` and are
  hydrated with an explicit `client:*` directive. Everything else stays a static `.astro` component.
- `src/pages/api/**` route handlers validate their own input at the boundary; they call into
  `src/libs` for anything reusable (e.g. sending email via `src/libs/email`) rather than inlining
  it.
- Brand-specific content, styling, and config live under `src/assets/<brand>/` (`content`, `fonts`,
  `images`, `logo`, `menus`, `styles`, plus that brand's own `wrangler.jsonc`). Shared code
  (`src/libs`, `src/components`, `src/layouts`) must not hardcode a specific brand — it reads
  brand data through the `@brand/*` alias / brand resolution, not a hardcoded path.

## Where things go

- `src/pages/` — routes; `src/pages/api/` — API endpoints (e.g. `src/pages/api/booking`)
- `src/components/` — Astro components; `src/components/client/` — React islands (hydrated)
- `src/layouts/` — shared page layouts
- `src/libs/email/` — outbound email (templates in `src/libs/email/templates`)
- `src/libs/types/` — shared TypeScript types/schemas
- `src/libs/utils/` — pure utility functions
- `src/assets/<brand>/` — per-tenant content, fonts, images, logo, menus, styles, and that brand's
  `wrangler.jsonc` (this repo is multi-tenant/whitelabel — not a monorepo, one Astro codebase
  serving several restaurant brands, each deployed as its own Cloudflare Worker)

## Anti-patterns (reject in review)

- Business logic (pricing, validation, brand resolution) written inline in `.astro` frontmatter or
  a React island instead of `src/libs` — untestable and hard to reuse.
- A shared component (`src/components`, `src/layouts`) hardcoding one brand's content/copy/styling
  instead of reading it from `src/assets/<brand>`.
- Hydrating a component with `client:load` (or any `client:*` directive) when it has no
  interactivity — unnecessary JS shipped to the browser.
- An API route in `src/pages/api` calling out to a third-party service (e.g. email) without going
  through `src/libs` — duplicated logic and no single place to test/mock it.
